# Целевая архитектура Personal Expert AI

**Статус:** согласованная целевая архитектура продукта.  
**Назначение:** зафиксировать роли компонентов и границы ответственности, чтобы дальнейшая разработка отдельных подсистем не уводила проект от общей цели.

## 1. Видение продукта

Personal Expert AI — локальная AI-платформа, которая объединяет пользовательский интерфейс, собственную Python-оркестрацию, инженерное ядро, память, управление знаниями и локальные AI-модели.

Это не просто чат с загруженными файлами. Система должна накапливать и использовать три независимых, но взаимодействующих вида памяти:

1. **User Memory — пользовательская память:** профиль, предпочтения, рабочий контекст и подтверждённые сведения о способе взаимодействия.
2. **Project Memory — проектная память:** документы и их версии, структура проекта, технические решения, переписка, история изменений, выводы и связи.
3. **Professional Memory — профессиональная память:** проверенные знания, инженерные методы, нормативные правила, навыки и результаты, пригодные для повторного применения.

Память не подменяет первичные источники и не становится самостоятельным источником инженерной истины. Для значимых выводов сохраняются происхождение, версия и доказательства; критические изменения и перенос знаний проходят контролируемое подтверждение.

## 2. Логическая архитектура

```text
Personal Expert AI
│
├── Bionic fork (customized UI + agent runtime, POC)
│   ├── Пользовательский интерфейс Personal Expert AI
│   ├── Agent harness / Skills / tool runtime
│   └── API adapter to Personal Expert AI backend
│
├── Python AI Orchestrator
│   ├── Управление задачами и workflow
│   ├── Маршрутизация запросов к моделям
│   ├── Управление контекстом и памятью
│   ├── Вызов Skills и MCP Tools
│   ├── Контроль прав, подтверждений и аудита
│   └── API для UI и внутренних компонентов
│
├── Project Expert Engine
│   ├── Document Processing Pipeline
│   ├── Извлечение текста, таблиц, формул, изображений и геометрии
│   ├── Структурированная модель документа и страницы
│   └── Инженерный анализ и проверки
│
├── Memory Engine (Hermes-inspired)
│   ├── User Memory
│   ├── Project Memory
│   ├── Professional Memory
│   ├── Session / Task Memory
│   └── Skills Registry и история исполнений
│
├── Knowledge Engine
│   ├── Структурированные знания и утверждения
│   ├── Hybrid retrieval / full-text / vector search
│   ├── Типизированные связи и граф знаний
│   └── Provenance, конфликты и версии
│
├── MCP Tools / Tool Gateway
│   └── Контролируемые инструменты и интеграции
│
└── Local AI Runtime — LM Studio
    ├── Qwen и другие локальные LLM
    ├── Embedding models
    ├── Vision-language models
    └── Reranker models

Cross-cutting infrastructure:
- PostgreSQL — источник истины для метаданных, доступа, памяти,
  диалогов, задач, знаний и результатов.
- Local filesystem/object storage — оригиналы документов и артефакты.
- Security / tenant isolation / audit / backup / observability.
```

Это логическая схема ответственности, а не требование развернуть каждый компонент как отдельный процесс или сервис. На ранних этапах несколько подсистем могут работать внутри одного Python backend, сохраняя модульные границы.

## 3. Ответственность компонентов и архитектурные границы

### Bionic fork — интерфейс и экспериментальная агентная среда первого этапа

- Отдельный форк upstream Bionic с интерфейсом Personal Expert AI.
- На первом этапе сохраняются agent harness, Skills и tool runtime; кастомизация ограничивается branding, навигацией, project/document workspace, chat и evidence presentation.
- Не владеет доменной моделью, инженерными правилами, оригиналами документов и основным жизненным циклом документов.
- Не получает прямого доступа к PostgreSQL Personal Expert AI; интеграция выполняется через authenticated API adapter.
- Решение о production-использовании принимается только после runtime POC, проверки безопасности и regression tests.
- Backend и экспертное ядро должны оставаться независимыми от Bionic, чтобы UI/runtime можно было заменить без переписывания доменной логики.

### Python AI Orchestrator — центральный управляющий слой

- Принимает запросы UI и внутренних компонентов.
- Определяет сценарий, контекст, нужные Skills, инструменты и модели.
- Управляет последовательностью операций и передачей данных между подсистемами.
- Проверяет полномочия и требует подтверждения для чувствительных действий.
- Записывает события и результаты исполнения.
- Не дублирует специализированную логику Project Expert Engine и Knowledge Engine.

### Project Expert Engine — инженерное и документное ядро

- Обрабатывает проектные документы и их редакции.
- Сохраняет точную связь извлечённых данных с исходным документом, версией, страницей, листом, таблицей и координатами.
- Формирует структурированное представление документов и проекта.
- Выполняет специализированные инженерные проверки.
- Существующие наработки Project Expert AI переносятся и интегрируются модульно; работающие механизмы не переписываются без необходимости.

### Memory Engine — собственная память с идеями Hermes

Hermes Agent используется как источник архитектурных идей для persistent memory, Skills и накопления опыта. Запуск самого Hermes как обязательного постоянно работающего агента не требуется.

- Разделяет пользовательскую, проектную, профессиональную, сессионную и задачно-ориентированную память.
- Хранит provenance, scope, актуальность, подтверждение, версию и правила удаления.
- Не смешивает подтверждённые факты, предположения и временный контекст.
- Skills имеют версии и контролируемые права исполнения.

### Knowledge Engine — управление знаниями

- Хранит структурированные сущности, утверждения и отношения.
- Поддерживает полнотекстовый, векторный и гибридный поиск.
- Позволяет строить граф связей между документами, требованиями, решениями и доказательствами.
- Сохраняет provenance и противоречия.
- Выбор vector/graph технологий делается после benchmark; PostgreSQL остаётся источником истины.

### MCP Tools / Tool Gateway

- Предоставляет стандартный способ подключения инструментов и интеграций.
- Вызовы проходят через allowlist, проверку полномочий, ограничения аргументов и аудит.
- Содержимое документов рассматривается как недоверенные данные, а не как инструкции для инструментов или агента.

### LM Studio — локальная инфраструктура моделей

LM Studio принимается как первый локальный runtime за собственной provider abstraction.

Планируемые возможности:
- LLM для диалога, анализа и планирования;
- embeddings;
- vision-language models;
- reranker;
- tool calling и streaming, если они поддерживаются выбранной моделью/runtime.

Конкретные модели, параметры, параллелизм и производительность выбираются экспериментально. Backend не должен зависеть от LM Studio-specific API за пределами адаптера провайдера.

### Bionic

Bionic рассматривается как upstream-основа отдельного форка с адаптированным интерфейсом Personal Expert AI и экспериментальным agent runtime. До завершения POC он не является production-зависимостью и не владеет памятью, документами или бизнес-логикой платформы. Границы интеграции, план кастомизации и критерии приёмки описаны в docs/integrations/bionic/.

## 4. Принципы обработки документов

Внутри Project Expert Engine применяется конвейер:

```text
Original document + immutable version
        ↓
Format adapters and native extraction
        ↓
Page rendering / OCR / image extraction
        ↓
Tables / formulas / vector graphics / Vision
        ↓
Unified Document and Page Model
        ↓
Quality and completeness assessment
        ↓
Source fragments + provenance
        ↓
Knowledge extraction and indexing
        ↓
Project Memory / Knowledge Engine
        ↓
Orchestrated Q&A and engineering review
```

OCR — только один из адаптеров извлечения, а не самостоятельный продуктовый контур. Vision-модель дополняет структурное извлечение семантическим анализом, но не заменяет детерминированные парсеры, координаты и проверяемые источники.

## 5. Данные и безопасность

- PostgreSQL — источник истины для пользователей, tenant/project access, документов и версий, задач, фрагментов, знаний, памяти, диалогов и аудита.
- Оригиналы и производные бинарные артефакты хранятся локально с checksum и контролем целостности.
- Vector store и graph store являются производными индексами, которые можно пересоздать из первичных данных.
- Tenant и project isolation проверяются на API, repository/service и storage boundaries.
- Документы, OCR-текст и извлечённые инструкции считаются недоверенным содержимым.
- По умолчанию обработка и inference локальные; любые внешние интеграции требуют явного контроля и документированной сетевой политики.

## 6. Правила выбора технологий

1. Не добавлять библиотеку в основной runtime только из-за популярности.
2. Сначала проводить изолированный benchmark на репрезентативных данных.
3. Оформлять существенный выбор через ADR: альтернативы, критерии, результаты, риски и условия пересмотра.
4. Сохранять сменные adapters/providers и не связывать доменную логику с конкретным runtime.
5. Не считать документацию или наличие интерфейса доказательством готовности функции.
6. Пункт roadmap закрывается только после реализации, тестов и зафиксированных результатов.

## 7. Не входит в обязательную архитектуру

- Запуск Hermes Agent как обязательного постоянного процесса.
- Bionic как обязательный production-компонент.
- AnythingLLM как владелец доменной логики, памяти или инженерной экспертизы.
- Единственная внешняя vector/graph база как источник истины.
- Облачная LLM как обязательная зависимость.

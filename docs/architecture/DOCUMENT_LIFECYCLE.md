# Document Lifecycle — жизненный цикл документа

- Статус: базовая архитектурная спецификация, версия 1.0
- Дата: 2026-11-01

## 1. Цель

Обеспечить контролируемый путь от загрузки оригинала до доступного для поиска цифрового представления, не теряя структуру, происхождение, геометрию и связь с исходной редакцией.

## 2. Состояния документа и версии

Логический Document существует независимо от конкретного файла. Каждая загрузка создаёт DocumentVersion. Рекомендуемые состояния версии:

uploaded → quarantined/validating → queued → processing → quality_check → indexed → current/superseded → archived.

Альтернативные терминальные состояния: rejected, failed, deleted_pending, deleted.

ProcessingRun имеет собственный статус и может быть повторён с новым pipeline version. Неудачный запуск не должен уничтожать оригинал или предыдущую успешную индексацию.

## 3. Этапы pipeline

### 3.1 Приём и регистрация
- Проверить аутентификацию, project access, квоты и лимиты.
- Принять файл потоково, не загружая весь файл в память без необходимости.
- Нормализовать имя только для отображения; storage key генерировать независимо.
- Определить MIME/type по содержимому, проверить расширение и допустимые форматы.
- Проверить размер, checksum, архивные контейнеры и признаки вредоносного содержимого.
- Сохранить оригинал в карантинной области до успешной валидации.
- Создать DocumentVersion и AuditEvent.

### 3.2 Дедупликация
Вычислить криптографический checksum исходных байтов. Совпадение checksum может выявить идентичный файл, но не означает автоматически, что это одна логическая редакция или один документ. Пользователь/сервис принимает решение о связывании.

### 3.3 Извлечение и классификация
Определить формат и выбрать адаптер:
- PDF: текстовый слой, страницы, встроенные изображения, векторные элементы, координаты, таблицы.
- DOCX: заголовки, абзацы, таблицы, колонтитулы, изображения и связи.
- XLSX: листы, именованные диапазоны, ячейки, формулы, значения, merged cells.
- PPTX: слайды, текстовые блоки, таблицы, изображения.
- Растровые изображения: ориентация, разрешение, OCR и геометрические области.
- CAD/BIM (DWG/IFC и другие): отдельные специализированные адаптеры; не считать поддержку реализованной до тестов.

Для PDF сначала извлекается native text/vector content. OCR — fallback или параллельный метод контроля качества, а не безусловная замена исходного текстового слоя.

### 3.4 Нормализация
Создать унифицированные элементы:
- DocumentStructureNode — раздел, подраздел, страница, лист, таблица и т.п.
- SourceFragment — минимальная цитируемая единица.
- Asset — изображение, crop, preview или иной бинарный производный объект.
- Table — структурированная сетка с ячейками и координатами.
- Formula — текстовое/машиночитаемое представление с provenance.
- DrawingElement — распознанная геометрия/подпись с локатором.

Нормализация не должна удалять исходное представление. Хранятся raw extraction и normalized representation с версиями схем.

### 3.5 Обогащение
Допускается LLM/vision для классификации, описания страницы, извлечения сущностей и интерпретации сложной структуры. Каждый результат помечается как машинный, содержит модель/версию/промпт, confidence или quality indicators и ссылки на исходные фрагменты. LLM не должна создавать факт без привязки к источнику.

### 3.6 Контроль качества
Проверять:
- количество страниц/листов и полноту обхода;
- наличие пустых/непрочитанных страниц;
- качество OCR и подозрительные символы;
- корректность координат и поворотов;
- целостность таблиц, формул и изображений;
- соответствие фрагментов исходной версии;
- ошибки и warnings отдельных этапов.

Качество документа и уверенность отдельного факта — разные показатели. Низкое качество должно ограничивать допустимость последующих выводов.

### 3.7 Индексация
Создать:
- точный индекс идентификаторов, шифров, обозначений и нормативных ссылок;
- полнотекстовый индекс;
- семантические embeddings, если включены и доступны локально;
- структурные индексы по разделам, таблицам, страницам и сущностям;
- связи между элементами проекта.

Индекс всегда фильтруется по tenant_id, project_id, document_version_id и правам. Индексация идемпотентна и привязана к версиям parser/model/embedding.

### 3.8 Публикация
После успешного quality gate версия становится searchable. Переключение current version — отдельная операция. При частичном успехе UI показывает обработанные и необработанные части; система не выдаёт частичный индекс за полный.

## 4. Цифровой паспорт документа и проекта

Паспорт документа содержит:
- идентификацию и тип;
- источник, версию, дату, checksum;
- количество страниц/листов;
- структуру и состав;
- таблицы, изображения, формулы и чертежи;
- извлечённые сущности и утверждения;
- warnings, confidence/quality;
- историю обработки и версии pipeline.

Паспорт проекта агрегирует состав документации, разделы, взаимосвязи, актуальные редакции, основные параметры, выявленные противоречия, пробелы данных и результаты проверок. Паспорт — навигационное и аналитическое представление, а не замена оригинальных документов.

## 5. Локаторы и доказательства

Локатор должен быть достаточен для повторного открытия места в исходнике. Для PDF хранить page index/page label, bbox, rotation, размеры страницы и coordinate system. Для таблиц — sheet/page, table id, row/column/cell. Для DOCX/XLSX — структурный путь/диапазон.

BBox нормализуется в документированной системе координат и преобразуется к preview только через единый geometry adapter. В EvidenceLink хранится ссылка на SourceFragment, а не скопированный текст без provenance.

## 6. Новые редакции и сравнение

Новая редакция создаёт новый DocumentVersion и отдельный ProcessingRun. Система может сравнивать структуру, текст, таблицы, изображения и извлечённые значения. Результат diff сам является производным артефактом и ссылается на обе версии. Автоматически переключать current version можно только по явно заданной политике; по умолчанию пользователь подтверждает.

## 7. Ошибки и повторные запуски

Каждый этап имеет собственный error code, retry policy и диагностику. Retry не должен создавать дубли SourceFragments или индексов. Для несовместимой новой версии parser создаётся новый ProcessingRun, прежние артефакты сохраняются для аудита/сравнения до окончания retention.

## 8. Удаление и retention

Удаление включает:
1. проверку прав и подтверждение;
2. перевод версии в deleted_pending;
3. блокирование новых retrieval;
4. удаление/инвалидацию embeddings, FTS, previews, crops и кэшей;
5. удаление оригинала и производных объектов согласно retention policy;
6. фиксацию минимального AuditEvent без сохранения содержимого документа.

Юридические/организационные требования к срокам хранения, резервным копиям и окончательному удалению должны быть определены владельцем установки. Удаление из основной БД не означает мгновенное исчезновение из резервной копии; этот срок раскрывается администратору.

## 9. Защита от вредоносного содержимого и prompt injection

Файлы и их содержимое — недоверенные данные. Парсеры работают с ограничениями ресурсов и по возможности в sandbox. Текст документа никогда не становится системной инструкцией. Скрытые инструкции в PDF, OCR, таблицах или изображениях не могут менять права, вызывать инструменты или отправлять данные. Вызов инструмента возможен только через backend policy engine.

## 10. Метрики и критерии качества

Для каждого формата формируется benchmark с ground truth:
- полнота извлечения текста/страниц;
- точность структуры;
- table cell accuracy;
- formula fidelity;
- OCR quality;
- locator/BBox accuracy;
- source citation accuracy;
- processing time и memory footprint.

Сравнение AnythingLLM и Project Expert AI проводится на одном обезличенном корпусе и одинаковых критериях. Средний score не должен скрывать критические ошибки отдельных типов данных.

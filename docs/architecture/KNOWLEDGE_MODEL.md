# Knowledge Model — структура знаний проекта

- Статус: базовая архитектурная спецификация, версия 1.0
- Дата: 2026-11-01

## 1. Назначение

Knowledge Model — структурированное представление сведений о проекте, извлечённых из документов, подтверждённых пользователем или полученных проверочными процедурами. Она объединяет поиск по тексту с типизированными объектами, утверждениями, связями и доказательствами.

Knowledge Model не является «истиной, созданной нейросетью». Это слой утверждений с явным происхождением, статусом и степенью подтверждения.

## 2. Слои знаний

1. **Source layer** — неизменяемые документы и DocumentVersion.
2. **Fragment layer** — SourceFragments с локаторами и исходными координатами.
3. **Extraction layer** — машинные результаты парсеров, OCR, vision и LLM.
4. **Assertion layer** — атомарные утверждения с источниками и статусом.
5. **Canonical project layer** — согласованные сущности и значения проекта.
6. **Relationship layer** — связи между разделами, элементами и утверждениями.
7. **Derived layer** — summaries, embeddings, graph projections, индексы и аналитика.
8. **Review layer** — результаты инженерных проверок и доказательные ссылки.

## 3. Типы знаний

- ProjectFact — параметр/характеристика проекта.
- DocumentFact — реквизит или свойство документа.
- DesignDecision — принятое проектное решение.
- Requirement — требование из нормы, ТЗ или исходных данных.
- NormativeReference — ссылка на нормативный источник с редакцией и применимостью.
- Equipment — оборудование и его характеристики.
- Material — материал и свойства.
- Space/Room — помещение, зона или пространство.
- System — инженерная система.
- Element — строительный/инженерный элемент.
- Quantity — величина с единицей измерения и контекстом.
- Formula — формула/выражение с переменными и источником.
- TableRecord — запись из таблицы с координатами ячеек.
- DrawingAnnotation — подпись/обозначение на чертеже.
- Conflict — противоречащие утверждения.
- EvidenceGap — требуемое, но не найденное доказательство.

Схема типов расширяется по разделам ВК, КР, АР, ЭОМ и другим дисциплинам; общие типы не должны содержать специфические поля, не применимые к другим разделам.

## 4. Атомарное утверждение

Каждое утверждение хранит:
- subject/entity;
- predicate/attribute;
- value;
- unit и dimensional context при необходимости;
- scope (проект, раздел, документ, помещение, система, элемент);
- source_fragment_id;
- extraction_method и extractor_version;
- confidence/quality indicators;
- validity period или version applicability;
- status: proposed, accepted, rejected, superseded, disputed;
- reviewer и timestamp, если подтверждено человеком.

Пример:
```json
{
  "kind": "ProjectFact",
  "subject": "building.level.1",
  "predicate": "finished_floor_elevation",
  "value": 0.000,
  "unit": "m",
  "scope": {"discipline": "АР", "level": "1"},
  "status": "proposed",
  "provenance": {
    "document_version_id": "uuid",
    "source_fragment_id": "uuid",
    "method": "table_parser"
  }
}
```

Это иллюстративная форма, не окончательная схема API/БД.

## 5. Provenance — происхождение

Для каждого значения нужно отвечать:
- из какого файла и редакции оно получено;
- где именно находится (страница, лист, ячейка, bbox);
- каким методом извлечено;
- какой parser/model/prompt version использовался;
- было ли проверено человеком;
- какие преобразования единиц или нормализация применялись.

Производное значение должно сохранять цепочку происхождения до исходного SourceFragment. Сводный текст без ссылок не может быть единственным основанием инженерного вывода.

## 6. Канонизация и конфликты

Один параметр может встретиться в нескольких документах, редакциях и разделах. Каноническое значение не выбирается по принципу «последний найденный текст» или «наибольшая уверенность модели».

Алгоритм:
1. Сформировать отдельные утверждения для каждого источника.
2. Нормализовать обозначения, единицы и контекст, сохранив исходное значение.
3. Сопоставить scope и version applicability.
4. Определить совместимость значений и допуски, если они определены инженерным правилом.
5. При противоречии создать Conflict и сохранить все утверждения.
6. Применить явное правило приоритета источников, если оно утверждено для данного типа сведений.
7. При отсутствии правила запросить решение человека.

Нельзя автоматически объявлять конфликтом различия, объясняемые разными стадиями, масштабами, системами координат или датами применимости.

## 7. Связи между элементами проекта

Типы отношений должны быть типизированы и иметь направление/семантику, например:
- belongs_to_section;
- described_by;
- located_in;
- feeds_into / supplied_by;
- connected_to;
- references;
- derived_from;
- supersedes;
- conflicts_with;
- constrains;
- implemented_by;
- verified_by.

Связь содержит source, target, relation_type, provenance, validity и status. Автоматически предложенная связь отличается от подтверждённой. Система не должна создавать связи только по совпадению слов без контекстной проверки.

## 8. Гибридный retrieval

Ответ на вопрос может комбинировать:
- точный поиск по шифрам, маркам, номерам листов и нормативным пунктам;
- полнотекстовый поиск;
- фильтрацию по разделу, документу, редакции и статусу;
- семантический поиск;
- поиск по таблицам/структуре;
- обход подтверждённых связей;
- reranking найденных фрагментов.

Результат retrieval — набор кандидатов, не готовые доказательства. Перед генерацией ответа backend проверяет права, актуальность, provenance и достаточность источников.

## 9. Контекст для LLM

Контекст формируется backend и содержит только разрешённые фрагменты. Каждый фрагмент имеет стабильный citation token, locator, document/version metadata и ограничения использования. Модель может ссылаться только на переданные токены. Backend валидирует, что citation действительно соответствует выданному фрагменту.

Документы и найденные фрагменты рассматриваются как недоверенное содержимое. Инструкции, обнаруженные внутри документов, не меняют системный prompt и не расширяют доступ к инструментам.

## 10. Качество и неопределённость

Необходимо различать:
- confidence извлечения;
- качество исходного документа;
- relevance retrieval;
- согласованность нескольких источников;
- уверенность/обоснованность вывода.

Один общий «процент точности AI» недопустим без ясного определения. Если доказательств недостаточно, ответ должен явно обозначить пробел и предложить, какие документы/листы нужны.

## 11. Индексы и хранилища

На первом этапе реляционная модель и PostgreSQL FTS обеспечивают базовую структуру и точный поиск. pgvector сравнивается с Qdrant на одинаковом корпусе. Графовая БД не вводится, пока измерения не докажут преимущество над relational edges и recursive queries.

## 12. Применение в инженерной проверке

Review Engine получает snapshot знаний с фиксированными версиями документов, нормативных источников и Skills. Каждый Finding ссылается на:
- проверяемое требование/правило;
- фактические утверждения;
- источники и локаторы;
- метод проверки и версию;
- статус достаточности доказательств.

Категории результата должны различать реальное несоответствие, противоречие, отсутствие сведений, низкое качество извлечения и необходимость ручной проверки.
